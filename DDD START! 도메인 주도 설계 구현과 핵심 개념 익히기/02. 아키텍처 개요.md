## 아키텍처
도메인 모델은 계층 구조로, 4계층으로 구성된다. 

계층 구조는 상위 계층에서 하위 계층으로의 의존만 존재한다.   
하위 계층은 상위 계층에 의존하지 않는다. 


- presentation: 사용자의 요청을 받아 응용 영역에 전달하고 응용 영역의 처리 결과를 사용자에게 보여줌
- application: 사용자에게 제공할 기능 구현, 로직을 직접 수행하기 보다는 도메인 모델에 로직 수행 책임 위임
- domain: 도메인의 핵심 로직 구현
- infra: DB, message queue, 외부 API 등

## DIP
고수준 모듈이 저수준 모듈을 사용하면 두 가지 문제가 발생할 수 있다. 
- 구현 변경의 어려움
- 테스트의 어려움

위의 문제를 해결하기 위해 저수준 모듈이 고수준 모듈에 의존하도록 함.
-> 인터페이스 추상화

## 도메인 영역의 주요 구성요소

#### 엔티티
고유한 식별자를 갖는 객체로 라이프 사이클을 갖는다. 
도메인 모델의 데이터를 포함하며 해당 데이터와 관련된 기능을 제공한다.

#### 밸류
고유의 식별자를 갖지 않는 객체.
개념적으로 하나의 값을 표현할 때 사용한다. 엔티티의 속성으로 사용하거나 다른 밸류 타입의 속성으로 사용한다.

#### 애그리거트
연관된 엔티티와 밸류 객체를 개념적으로 하나로 묶은 것으로 애그리거트마다 애그리루트가 존재한다.
외부에서는 반드시 애그리거트 루트롤 통해 내부에 접근이 가능핟다.

애그리거트를 사용하면 개별 객체가 아닌 관련 객체를 묶어서 객체 군집 단위로 모델을 볼 수 있다.
군집에 속한 객체를 관리하는 루트 엔티티를 가지며, 루트 엔티티는 애그리거트에 속해있는 엔티티와 밸류 객체를 
활용해 애그리거트가 구현해야할 기능을 제공한다. 

예)
'주문' 도메인 -> 주문, 배송지 정보, 주문자, 주문 목록, 결제 금액 등의 하위 모델로 구성


#### 레포지토리
도메인 모델을 영속화(DB 저장/조회)하는 역할
도메인 입장에서는 저장소 느낌?

#### 도메인 서비스
어떤 엔티티 하나에 넣기 애매한 도메인 로직을 처리하는 곳
여러 엔티티를 조합하거나 복잡한 비즈니스 규칙을 담당한다.

   
예)
- 두 사용자의 거래 가능 여부를 판단하는 서비스
- 할인 적용 가능 여부를 판단하는 서비스


-> 상태를 갖지 않고 순수 기능만 갖는다.


---
#### DB 테이블의 엔티티와 도메인 모델의 엔티티?
가장 큰 차이점은 도메인 모델의 엔티티는 데이터와 함께 도메인 기능을 함께 제공한다.
또, 도메인 모델의 엔티티는 두 개 이상의 데이터가 개념적으로 하나인 경우 밸류 타입을 이용해서 표현할 수 
있다는 것이다.

## 인프라스트럭처
도메인 영역과 응용 영역에서 인프라의 기능을 직접 사용하는 것보다는 인터페이스를 인프라 영역에서 
구현하는 것이 시스템이 더 유연하고 테스트하기 쉽도록 만든닫.

하지만, 무조건 인프라에 대한 의존을 없앨 필요는 없다. 
구현의 편리함(ex. @Transactional, @Entity..)은 DIP가 주는 다른 장점(변경의 유연함, 테스트 용이)만큼 중요하기 때문에
DIP의 장점을 해치지 않는 범위에서 응용 영역과 도메인 영역에서 구현 기술에 대한 의존을 가져가는 것은 나쁘지 않다.
