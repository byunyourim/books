# 도메인

도메인은 해결하고자 하는 문제의 영역으로 여러 하위 도메인으로 나눌 수 있다.   
예) 온라인 서점 -> 주문, 회원, 리뷰, 정산, 배송 등



<br>

**도메인 모델**은 특정 도메인을 개념적으로 표현한 것으로, 바로 코드로 쓸 수 없고 구현 모델로 발전시켜야 한다. 


<br>

## 도메인 모델 패턴
도메인 모델은 4계층으로 구성이된다. 
- Presentation: 컨트롤러, 사용자 요청, 응답 처리
- Application: 기능 조합, 흐름 관리
- Domain: 비즈니스 규칙
- Infrastructure: DB, 메시지 시스템, 외부 API

핵심 규칙은 도메인 계층에만 존재함.  

예) 주문 취소는 배송 전에만 할 수 있다.



<br>

## 엔티티와 밸류
엔티티는 고유한 식별자(ID)를 갖는다. 
식별자는 엔티티 객체마다 고유한 값으로, 각 엔티티는 서로 다른 식별자를 갖는다. 
엔티티를 생성, 변경, 삭제 할 때까지 유지된다. 

특정 규칙에 따라 생성할 수도 있고, UUID 등 고유 생성기를 사용할 수도 있다. 

밸류는 식별자없이 값과 의미를 갖는다. 

   
예) 배송지의 경우, 배송지 자체를 ID로 관리할 필요가 없기 때문에 밸류 객체이다.    
사람 User, 주문 Order은 각각 구분을 위해 ID가 필요하기 때문에 엔티티이다.   
   
밸류 객체는 보통 불변(immutable)로 설계하는 것이 정석이다.





<br>

## 유비쿼터스 언어
개발자, 도메인 전문가, 관계자가 모두 이해할 수 있는 공통의 용어로 소통하고, 그 용어를 코드에 반영해야 한다. 

예) 
- step1, step2, step3 ... -> 이해 X,
- PAYMENT_WAITING, PREPARING< SHIPPED -> O

-> 소통의 오류를 방지하고 코드와 비즈니스의 의미를 일치시킴.



도메인 모델은 문제 영역을 개념적으로 표현한 것이고, 이를 기반으로 계층 구조와 유비쿼터스 언어를 이용하여
안정적인 소프트웨어를 만드는 것이 DDD의 핵심이다.
