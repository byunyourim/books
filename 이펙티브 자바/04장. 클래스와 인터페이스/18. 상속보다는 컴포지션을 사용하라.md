
#### 상위클래스의 구현에 따라 하위 클래스에 이상이 생길 수 있다. 
- 상위 클래스가 어떻게 구현되느냐에 따라 하위 클래스의 동작에 이상이 생길 수 있다.
- 릴리스마다 내부 구현이 달라질 수 있으며, 그 여파로 코드 한 줄 건드리지 않은 하위 클래스가 오동작할 수 있다.


```java
public class InstrumentedHashSetUseExtends<E> extends HashSet {
    private int addCount = 0; // 추가된 원소의 수

    public InstrumentedHashSetUseExtends() {
    }

    public InstrumentedHashSetUseExtends(int initCap, float loadFactor) {
        super(initCap, loadFactor);
    }

    @Override
    public boolean add(Object o) {
        return super.add(o);
    }

    @Override
    public boolean addAll(Collection c) {
        return super.addAll(c);
    }

    public int getAddCount() {
        return addCount;
    }

}
```
위 클래스의 인스턴스에 addAll 메서드를 사용하면 제대로 작동하지 않는다.




### 다음 릴리스에서 상위 클래스에 새로운 메서드를 추가한다면?
새롭게 추가된 메서드를 통해서 허용되지 않은 동작을 수행할 수 있게 될 수도 있다.
만약 하위 클래스에 추가한 메서드와 상위 클래스에 새롭게 추가된 메서드의 시그니처가 같고 반환 타입이 다르다면 컴파일조차 되지 않는다.
하위 클래스에 메서드를 작성할 때는 상위 클래스의 메서드는 존재하지도 않았으니, 하위 클래스의 메서드는 상위 클래스에 새롭게 추가된 메서드가 요구하는 규약을 지키지 못할 가능성이 크다.

### 컴포지션(has-a)을 이용하자.?
기존 클래스를 확장하는 대신, 새로운 클래스를 만들자.  
부모 클래스의 기능을 그대로 두기때문에 상속처럼 부모의 기능이 바뀌지 않는다. 약한 결합이라고 할 수 있다.

상속은 확장의 개념이라면, 컴포지션은 위임을 이용한다.

위임은 하위 클래스에서 상위클래스의 책임을 대신 위임받아 사용하는 것을 말한다. 이 때 상위 클래스가 재정의되거나 하는 일이 없어서 상위 클래스의 캡슐화가 지켜진다.
```java
public class Engine {
    public void start() {
        System.out.println("Engine started.");
    }

    public void stop() {
        System.out.println("Engine stopped.");
    }
}

public class Car {
    private Engine engine;

    public Car() {
        this.engine = new Engine();
    }

    public void startCar() {
        engine.start();  // Engine의 start 메서드 호출
        System.out.println("Car is moving.");
    }

    public void stopCar() {
        engine.stop();  // Engine의 stop 메서드 호출
        System.out.println("Car has stopped.");
    }
}
```
private 필드로 기존 클래스의 인스턴스를 참조한다. 
기존 클래스가 새로운 클래스의 구성요소로 사용된다고 해서 컴포지션(composition; 구성)이라 한다. 
   
위의 Car 클래스는 Engine 클래스를 컴포지션 방식으로 포함한다. Engine을 생성자로 초기화하여, Car 클래스의 메서드에서 사용한다. 

   
#### 전달과 전달 메서드 
이 방식을 전달(forwarding)이라 하며, 새 클래스의 메서드들을 전달 메서드(forwarding method)라 부른다.
그 결과 새로운 클래스는 기존 클래스의 내부 구현 방식의 영향에서 벗어나며, 심지어 기존 클래스에 새로운 메서드가 추가되더라도 전혀 영향받지 않는다.

이렇게 새로운 클래스가 기존 클래스의 메서드를 그대로 호출하는 방식을 전달이라고 한다. 
새로운 클래스는 기존 클래스의 메서드를 직접 호출하여 기능을 전달하는데, 이를 전달 메서드라고 한다.
이 방식은 새로운 클래스가 기존 클래스의 내부 구현에 의존하지 않기 때문에 기존 클래스에 새로운 기능이 추가되더라도, 새로 만든 클래스에는 영향을 미치지 않는다.

#### 컴포지션 방식(래퍼 클래스)
예를 들어 Set 클래스처럼 기존 객체를 감싸는 새로운 클래스를 만들면, 기존 기능에 새로운 기능을 추가할 수 있다. 이렇게 기존 클래스를 감싸는 클래스를 래퍼클래스라고 하고, 데코레이터 패턴이라고도 한다.
   
데코레이터 패턴은 기존 클래스에 기능을 추가하는 방식으로, 클래스가 추가적인 기능을 가지게 되어 유연성과 재사용성이 높다.

<br>

**하지만 콜백 프래임워크와 잘 맞지않을 수 있다.**  

콜백 프레임워크는 주로 이벤트 기반, 비동기 방식에서 "특정 이벤트가 발생했을 때 호출할 메서드를 미리 등록해두는" 구조로, 이벤트가 발생하면 콜백 메서드가 호출된다.  

"어디서, 언제 호출될지 모르는 메서드들"을 다루기 때문에, 전달 메서드 방식과 잘 맞지 않을 수 있다.
왜냐면, 전달 메서드는 메서드를 호출하는 순서가 예측 가능한 구조로 콜백 프레임워크와는 설계적인 측면에서 차이가 있기 때문이다.

즉, 콜백 방식에서는 호출될 메서드가 즉시 실행되지 않거나 나중에 호출되기 때문에, 기존 클래스의 메서드를 단순히 전달하는 방식이 복잡하거나 불편할 수 있다.


#### 래퍼 클래스와 SELF 문제
콜백 프레임워크에서는 자기 자신의 참조를 다른 객체에 넘겨서 다음 호출(콜백) 때 사용한다.

**내부 객체는 자신을 감싸고 있는 래퍼의 존재를 모른다.**
따라서 자신(this)의 참조를 넘기고, 콜백 때는 래퍼가 아닌 내부 객체를 호출하게 되는데, 이를 SELF 문제라고 한다.
```java
class WrappedObject {
    void callback() {
        System.out.println("Called from inside the object!");
    }
}

class Wrapper {
    private final WrappedObject wrapped;

    public Wrapper(WrappedObject wrapped) {
        this.wrapped = wrapped;
    }

    void doSomething() {
        System.out.println("Wrapper is doing something.");
        wrapped.callback(); // 내부 객체의 메서드 호출
    }
}
```

#### SELF 문제
내부 객체가 외부 시스템이나 콜백을 호출할 때 this를 넘기면, 래퍼가 아닌 내부 객체가 전달된다.
따라서, 외부에서 래퍼의 추가 기능이 아니라 내부 객체의 원래 기능만 호출하게 된다.



#### 왜 문제인가?
래퍼를 쓰는 이유는 기능을 확장하거나 수정하려는 것인데, 내부 객체가 자신만 호출되게 만들면 이 의도가 깨진다.


#### 해결
이 문제를 해결하려면 내부 객체가 래퍼를 인식하지 못하게 설계해야 할 상황을 피하거나, SELF 문제를 고려한 특별한 설계를 한다.

예를 들어, 콜백 기반 설계가 필요한 경우 상속보다 다른 방법(예: 델리게이트)을 사용하는 것이 더 적합하다.

### 상속 vs 컴포지션
상속은 구체 클래스를 확장할 때마다 생성자를 따로 정의해야 한다.
컴포지션은 한 번 구현하면 다양한 Set 구현체에 재사용이 가능하며, 기존 생성자와도 호환이 가능하다.


<br><br><br>

### 상속 is-a
`A는 B이다`로 자식 클래스가 부모 클래스의 일종이다 라는 관계를 나타낸다. 
자식 클래스가 부모 클래스를 완전히 대체할 수 있어야 한다. 
상속은 부모 메서드의 기능을 완전히 내 것으로 재정의할 수 있다는 특징이 있다. 
바나나는 과일이다 -> banana exteds Fruit

#### 주의
- 상속을 잘못 구현하게 되면 부모의 세부 사항이 자식 클래스에 드러난다.
- 부모클래스를 수정하면 자식 클래스에서 예기치 못한 문제가 생길 수 있다.
- 부모 클래스의 문제를 자식이 그대로 물려 받는다. 


#### 상속이 잘못 사용된 예

2. Properties와 Hashtable

상속은 상위 클래스와 하위 클래스가 is-a 관계일 때 사용해야 하지만,
