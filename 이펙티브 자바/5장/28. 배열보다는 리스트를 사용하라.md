### 배열과 제네릭 타입의 차이 : 공변
> 공변 : 함께 변한다. 

배열은 공변으로, 배열의 타입이 부모-자식 관계를 따라간다.   

```java
String[] strings = {"hello", "world"};
Object[] objects = strings; // String[]은 Object[]의 자식이므로 허용
```

String[]은 Object[]의 자식 타입으로, 위 코드는 컴파일과 실행이 된다.


따라서, Sub가 Super의 하위 타입이라면 Sub[]는 배열 Super[]의 하위 타입이 된다.

반면, 제네릭은 불공변이다. 리스트의 경우 서로 다른 타입 Type1, Type2가 있을 때, List<Type1>은 List<Type2>의 하위 타입도 아니고 상위 타입도 아니다.

<br>

#### 공변으로 인한 배열에서의 문제
Long 저장소에 String을 넣을 수 없다.
- 런타임 실패
```java
Object[] objectArray = new Long[1];
objectArray[0] = "타입이 달라 넣을 수 없다."; // ArrayStoreException 발생
```
   
- 컴파일 실패
```java
List<Object> objectList = new ArrayList<>(); // 호환되지 않는 타입이다.
objectList.add("타입이 달라 넣을 수 없다.");
```

배열은 이런 오류 발생을 런타임시에 알 수 있지만 리스트를 사용하면 컴파일시에 바로 알 수 있다.



<br>

### 배열과 제네릭 타입의 차이 : 배열의 실체화

배열은 자신이 담을 원소의 타입을 인지하고 확인한다. 그래서 Long 타입 배열에 String 타입 데이터를 입력할 경우 ArrayStoreException이 발생한다.
   
반면, 리스트는 타입 정보가 런타임에는 소거된다. 따라서 원소 타입을 컴파일시에만 검사하며 런타임에는 알 수 없다.

이런 이유로 배열은 제네릭 타입(new List<E>[]), 매개변수화 타입(new List<String>[]), 타입 매개변수(new E[]) 로 사용할 수 없다. 이런 식으로 코드를 작성하려하면 제네릭 배열 생성 오류를 일으킨다.


> #### 소거
> 컴파일러가 제네릭 타입 정보를 컴파일 타임에만 사용하고 런타임에는 없애는 것이다. 
> 제네릭이 없는 옛날 코드에서도 새로 작성된 제네릭 코드가 동작되어야 하기 때문에, 런타임에는 제네릭 정보를
> 없애 공통된 형태로 동작되도록 하기 위함이다.

<br>

### 제네릭 배열을 허용하지 않는 이유?
배열은 런타임에 타입을 확인하지만, 제네릭은 컴파일 타임에 타입을 확인한다. 따라서 이 둘이 충돌하면 문제가 생길 수 있다.  
```java
List<String>[] array = new List<String>[10]; // 제네릭 배열 생성
Object[] objArray = array; // 배열은 공변이라 가능
objArray[0] = List<Integer>(); // 다른 타입의 리스트를 넣음
String s = array[0].get(0); // 런타임 에러 발생!
```
배열은 공변성 때문에 Object[]를 참조할 수 있고, List<String>[] 타입을 넣을 수 있다. 
그러면 런타임에 타입 에러가 발생할 위험이 생긴다. 즉, 안정성을 보장할 수 없다. 

제네릭 배열은 런타임에 ClassCastException이 발생할 수 있어 타입 안정성을 보장하지 못하고, 제네릭의 목적에 어긋나기 때문에 허용되지 않는다.

### 실체화 불가 타입
`E, List<E>, List<String>` 같은 타입을 실체화 불가 타입이라고 한다.
실체화 불가 타입이란 런타임에 타입 정보를 알 수 없는 제네릭 타입을 말한다.
  
매개변수화 타입 가운데 실체화될 수 있는 타입은 List<?>, Map<?,?> 같은 와일드카드 타입뿐이다.
이 타입들은 제네릭 타입 소거 이후에도 구체적인 타입 정보를 일부 유지한다.   

참고로, 배열은 비한정적 와일드카드로 만들수는 있지만 유용하게 쓰일 일은 거의 없다.

#### SafeVarargs
메서드 작성자가 **이 메서드는 타입 안전하다** 고 컴파일러에게 보장하는 어노테이션이다.  
가변 인수 메서드에서 발생하는 제네릭 경고를 억제한다.  

가변인수 메서드는 호출시 배열을 생성하는데, 이 배열의 원소 타입이 실체 불가 타입이면 컴파일러가 경고를 낸다.
타입이 안전하다고 확신할 때만 사용하고, 안전하지 않다면 사용하지 말자.  
   
   
@SafeVarargs를 사용하면 잠재적 오류에 대한 경고를 무시함으로써 해결할 수 있다. 만약, 메서드가 타입 안전하지 않다면 절대 @SafeVarargs를 사용해서는 안된다.

```java
public class SafeVars {
    @SafeVarargs
    public static void print(List... names) {
        for (List<String> name : names) {
            System.out.println(name);
        }
    }

    public static void main(String[] args) {
        SafeVars safeVars = new SafeVars();
        List<String> list = new ArrayList<>();

        list.add("b");
        list.add("c");
        list.add("a");
        print(list);
    }
}
```

#### 배열대신 컬렉션을 이용하자.  
배열로 형변환하 할 때 제네릭 배열 생성 오류나 비검사 형변화나 경고가 뜨는 경우 대부분 List<E>를 사용하자.  

```java
public class ListChooser {
    private final List<T> choiceList;

    public ListChooser(final Collection<T> choices) {
        this.choiceList = new ArrayList<>(choices);
    }
    
    public T choose(){
        Random random = ThreadLocalRandom.current();
        return choiceList[random.nextInt(choiceList.size())];
    }
}
```

### 마무리
배열과 제네릭에는 매우 다른 타입 규칙이 적용된다. 배열은 공변이고 실체화되는 반면, 제네릭은 불공변이고 타입 정보가 소거된다.
그 결과 배열은 런타임에는 타입 안전하지만, 컴파일 타임에는 그렇지 않다. 제네릭은 배열과 반대이다. 

그래서 둘을 섞어 쓰는 것은 어렵다. 
둘을 섞어 쓰다가 컴파일 오류나 경고를 만나면, 가장 먼저 배열을 리스트로 대체하는 방법을 적용해보자.
