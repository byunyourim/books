Finalizer는 예측 불가능하고, 위험할 수 있어 대부분 불필요하다.   
  
자바에서 제공하는 두 가지 객체 소멸자, finalizer와 cleaner는 기본적으로 **'쓰지 말아야'** 한다.  

<br><br><br><br><br><br>


#### 사용하지 말아야 하는 이유?
- **finalizer**: 예측할 수 없고, 위험할 수 있어 불필요하다.
- **cleaner**: finalizer보다 덜 위험하지만 여전히 예측할 수 없고, 느리고 불필요하다.







<br><br><br>

# finalizer, cleaner의 단점
### <mark>1. 수행 시점을 보장하지 않는다.</mark>
finalizer와 cleaner는 호출된 후 언제 실행될 지 알 수 없어, 제때 실행되어야 하는 작업을 절대 할 수 없다.  

finalizer와 cleaner의 얼마나 신속하게 수행할지는 GC 알고리즘에 달렸으면 GC 구현마다 다르다.  



### <mark>2. 자원 회수가 지연될 수 있다.</mark>
finalizer 스레드가 다른 애플리케이션 스레드 보다 우선 순위가 낮아 실행될 기회를 얻지 못할 수 있다. 
반면, cleaner는 자신을 수행할 스레드를 제어할 수는 있지만, 역시나 가비지 컬렉터에 의존하기 때문에 사용하지 않는다.


### <mark>3. 수행 여부를 보장하지 않는다.</mark>
두 작업은 GC가 객체를 수집할 때 실행되는데, GC가 언제 실행될지도 모르고, 실행되지 않을 수도 있다.  
즉, 객체가 제거될 때 필요한 정리 작업이 아예 무시될 수 있다.  

따라서 상태를 영구적으로 수정하는 작업(파일 저장, DB 업데이트)에서는 절대 finalizer와 cleaner를 사용하면 안된다.   


System.gc나 System.runFinalization 메서드는 GC 실행을 요청하지만, 강제는 아니다. JVM이 이 요청을
무시할 수 있어서 수행을 보장할 수 없다.  

System.runFinalizersOnExit와 Runtime.runFinalizersOnExit는 프로그램 종료시 모든 finalizer을 무조건 실행한다.
하지만, 다른 스레드가 해당 객체에 접근 중이라도 강제로 finalizer을 실행하기 때문에 위험하다.  

### <mark>4. 동작 중 발생한 예외가 무시된다.</mark>
finalizer는 예외가 발생해도 무시하고 작업을 종료하는데, 그러면 해당 객체는 마무리가 덜 된 상태로 남아있게 된다. 
그리고 다른 스레드가 이 훼손된 객체를 사용하게 되면 시스템이 불안정해질 수 있다.  
cleaner는 자신의 스레드를 통제하기 때문에 작업 도중 발생한 예외는 관리할 수 있다. 


### <mark>4. 심각한 성능 문제를 동반한다.</mark>
finalizer와 cleaner는 가비지 컬렉터의 효율을 떨어뜨린다.


### <mark>5.보안 문제를 일으킬 수 있다.</mark>
finalizer를 사용한 클래스는 finalizer 공격에 노출될 수 있다. 
<details>
  <summary><b>finalizer 공격 원리</b></summary>
객체가 완전히 생성되기 전에(생성자나 직렬화 중 예외 발생) 하위 클래스의 finalizer 메서드가
실행되어 예상치 못한 행동을 할 수 있다.  

finalizer 메서드가 객체를 정적 필드에 저장하면, GC가 삭제하지 못해 계속 남아있을 수 있다. 

이를 막을 방법으로는 클래스를 선언해 하위 클래스의 생성을 막을 수 있다.  
finalizer는 정적 필드에 자신의 참조를 할당하여 가비지 컬렉터가 수집하지 못하게 막을 수 있다.  

객체 생성을 막으려면 생성자에서 예외를 던지는 것만으로 충분하지만, finalizer가 존재하면 이를 완전히 차단할 수 없다. 
final 클래스는 하위 클래스를 만들 수 없기 때문에 finalizer 공격에 대해 안전하다.   
따라서 final이 아닌 클래스에서 finalizer 공격을 방어하려면, 
finalize 메서드를 아무 작업도 하지 않도록 작성하고, 클래스 자체를 final로 선언하면 된다. 

      
   



</details>

#### 파일이나 스레드 등 종료해야 할 자원을 담는 객체의 클래스에서 finalize, cleaner을 대신할 방법?

# AutoCloseable
종료해야 할 자원을 담고 있는 객체의 클래스에서 AutoCloseable을 구현하고,
클라이언트에서 인스턴스를 다 쓰고 나면 close 메서드를 호출하면 된다.  

예외가 발생해도 제대로 종료될 수 있도록 try-with-resources를 사용해야 한다. 

각 인스턴스는 자신이 닫혔는지를 추적하기 위해, close 메서드 호출 여부를 필드에 기록하고,
다른 메서드는 이 필드를 검사해서 객체가 닫힌 후에 불렸다면 IllegalStateException을 던지도록 한다.
    
<details>
  <summary><b>AutoCloseable 예제</b></summary>
  
```java
public class Resource implements AutoCloseable {
    private boolean closed = false;

    public void use() {
        if (closed) {
            throw new IllegalStateException("Resource is already closed!");
        }
        System.out.println("Using the resource...");
    }

    @Override
    public void close() {
        if (!closed) {
            closed = true;
            System.out.println("Resource closed.");
        }
    }
}
```

```java
public static void main(String[] args) {
    // try-with-resources 구문을 사용하여 자동으로 close() 호출
    try (Resource resource = new Resource()) {
        resource.use(); // 자원 사용
    } catch (Exception e) {
        e.printStackTrace();
    }
}
```
- close() 호출 여부를 추적해, 닫힌 후 잘못된 사용을 방지합니다.
- try-with-resources를 사용하면, 명시적으로 close()를 호출할 필요가 없고 안전하게 자원을 관리할 수 있습니다.
</details>

# finalizer와 cleaner는 언제 사용하나?
<mark>**첫 번째로, 사용자가 close메서드를 호출하지 않은 것에 대비한 "안전망" 역할이다.**</mark>
  
클라이언트가 하지 않은 자원 회수를 늦게라도 해주는 것이 아예 안 하는 것보다는 낫다.  
자바 라이브러리 일부 클래스는 안전망 역할의 finalizer을 제공한다.  
**ex) FileInputStream, FileOutputStream, ThreadPoolExecutor**  

<br>

<mark>**두 번째는 네이티브 피어(Native Peer)와 연결된 객체에서 사용된다.**</mark>  
네이티브 피어란, 자바 코드에서 사용하는 객체가 내부적으로 자바가 아닌 시스템의 네이티브 자원을 이용하도록
연결된 객체로, GC가 관리할 숫 없다. 따라서 즉시 회수해야 한다면 close 를 사용해야 한다.    

단, 성능 저하를 감당할 수 있고 네이티브 피어가 심각한 자원을 갖지 않을 때만 해당한다.  


<br><br>

**cleaner는 예제로 보자**


Room 인스턴스를 참조할 경우 순환참조가 생겨 GC가 Room인스턴스를 회수할 기회가 오지 않는다.  
  
State가 정적 중첩 클래스인 이유는
- 정적이 아닌 중첩 클래스는 자동으로 바깥 객체의 참조를 갖는다.
- 이와 비슷하게 람다 역시 바깥 객체의 참조를 갖기 쉬우니 사용하지 않는 것이 좋다.


```java
public class Room implements AutoCloseable{
    private static final Cleaner cleaner = Cleaner.create();

    // 수거할 자원. 절대 Room을 참조하면 안됨?
    private static class State implements Runnable {
        int numJunkPiles;

        State(int numJunkPiles) {
            this.numJunkPiles = numJunkPiles;
        }

        // close 메서드나 cleaner가 호출한다.
        @Override
        public void run() {
            System.out.println("방 청소");
            numJunkPiles = 0;
        }
    }

    // 방의 상태. cleanable과 공유
    private final State state;

    // cleanable 객체. 수거 대상이 되면 방을 청소한다.
    private final Cleaner.Cleanable cleanable;

    public Room(int numJunkPiles) {
        state = new State(numJunkPiles);
        cleanable = cleaner.register(this, state);
    }

    @Override
    public void close() throws Exception {
        cleanable.clean();
    }
}
```


<br><br><br>


클라이언트가 모든 Room 생성을 try-with-resources로 감쌌다면
자동 청소는 필요하지 않다. 
```java
class Adult {
    public static void main(String[] args) throws Exception {
        try (Room myRoom = new Room(7)){
            System.out.println("hi~!");
        }
    }
}
```
