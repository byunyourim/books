같은 기능의 객체를 새로 생성하는 대신 재사용하는 것이 나을 때가 많다.   
특히, 불변 객체는 언제든 재사용할 수 있다.

## 문자열 객체 생성
문자열 객체를 생성하는 방법은 두 가지가 있다.    
하나는 new 키워드를, 다른 하나는 리터럴로 생성하는 방법이다.   

#### new를 이용해 문자열 객체 생성
```java
String s = new String("hello");
```
위처럼 String객체를 new를 이용해서 생성하면 항상 새로운 객체를 만든다.  

<br>

#### 리터럴로 문자열 객체 생성
```java
String s = "hello";
```
이 코드는 하나의 String 인스턴스를 재사용하는 방식이다. 같은 가상 머신 안에서
같은 문자열 리터럴을 사용하는 모든 코드는 같은 객체를 재사용한다.

## static factory 메서드 사용
생성자 대신 정적 팩터리 메서드를 제공하는 불변 클래스에서는 불필요한 객체 생성을 피할 수 있다.  
생성자는 호출할 때마다 새로운 객체를 만들지만, 팩터리 메서드는 그렇지 않다.
```java
Boolean true1 = Boolean.valueOf("true");
Boolean true2 = Boolean.valueOf("true");

System.out.println(true1 == true2); // true
// Boolean(String) 생성자 대신 Boolean.valueOf(String) 팩터리 메서드 사용
```

<br>
<br>
<br>

생성 비용이 비싼 객체도 있는데, 비싼 객체가 반복적으로 필요한 경우에는 캐싱하여 재사용하는 것이 좋다.  

> **생성 비용이 높다?**    
> 객체를 생성할 때 메모리, CPU자원, 시간이 많이 소모된다는 의미로, 초기화 과정이 복잡하거나, 내부적으로 무거운 연산을 수행하는 경우 생성 비용이 높아진다.  


```java
static boolean isRomanNumeralSlow(String s) {
    return s.matches("^(?=.)M*(C[MD]|D?C{0,3})"
            + "(X[CL]|L?X{0,3})(I[XV]|V?I{0,3})$");
}
```
위의 코드는 String.matchees 메서드를 사용한다.
String.matches는 정규표현식으로 문자열 형태를 확인하는 방법으로 성능이 중요한 상황에서 반복해 사용하기 적합하지 않다.  

이 메서드가 내부에서 만드는 정규 표현식 Pattern 인스턴스는 한 번 쓰고 버려져 가비지 컬렉션 대상이 된다.  

Pattern은 생성 비용이 높은 클래스로 Pattern의 필요함이 보장되고 재사용 빈도가 높다면 상수(static final)로 초기에 캐싱해놓고 재사용할 수 있다.
```java
public class RomanNumerals {
    private static final Pattern ROMAN = Pattern.compile(
            "^(?=.)M*(C[MD]|D?C{0,3})"
                    + "(X[CL]|L?X{0,3})(I[XV]|V?I{0,3})$");

    static boolean isRomanNumeralFast(String s) {
        return ROMAN.matcher(s).matches();
    }
}
```
성능을 개선하려면 필요한 정규표현식을 표현하는 (불변인) Pattern 인스턴스를 클래스 초기화(정적 초기화) 과정에서 직접 생성해 캐싱해두고, 나중에 isRomanNumeral이 호출될 때마다 이를 재사용한다.

생성비용이 비싼 객체라면 "캐싱" 방식을 고려해야 한다.
자주 쓰는 값이라면 static final로 초기에 캐싱해놓고 재사용 하자.

만약 isRomanNumeral방식의 클래스가 초기화된 후 이 메서드가 한 번도 사용되지 않는다면, ROMAN 필드는 쓸데없이 초기화된 꼴이다.  
이럴때 지연 초기화로 불필요한 초기화를 없앨 수는 있지만, 코드는 복잡해지고 성능은 크게 개선되지 않아 권하지 않는다.

## Adaptor
불변 객체인 경우에 안전하게 재사용하는 것이 매우 명확하다.
하지만 어댑터의 경우 인터페이스를 통해 뒤에 있는 객체로 연결해주는 view라 여러 개 만들 필요가 없다.


Map 인터페이스의 keySet 메서드는 Map 객체 안의 키 전부를 담은 Set 인터페이스의 뷰를 반환한다.   
keySet을 호출할 때마다 새로운 set 인스턴스가 만들어질 거라 생각할 수 있지만, 반대로 매번 같은 Set 인스턴스를 반환할 수도 있다.  

물론 반환된 인스터스가 가변이더라도 기능은 모두 같다. 즉 반환 객체 중 하나를 수정하면 다른 모든 객체가 바뀐다.

즉, 동일한 Map에서 호출하는 keySet 메서드는 같은 Map을 대변하기 때문에 반환한 객체 중 하나를 수정하면 다른 모든 객체가 따라서 바뀐다.


따라서 keySet이 뷰 객체 여러 개를 만들 필요가 없다.

**같은 인스턴스를 대변하는 여러 개의 인스턴스를 생성하지 말자**
```java
Map<String, Object> map = new HashMap<>();
map.put("Hello", "World");

Set<String> set1 = map.keySet();
Set<String> set2 = map.keySet();

assertThat(set1).isSameAs(set2); // TRUE

set1.remove("Hello");
System.out.println(set1.size()); // 1
System.out.println(set1.size()); // 1
```
Map 인터페이스의 keySet 메서드는 Map 객체 안의 키 전부를 담은 Set 인터페이스의 뷰를 반환한다.
하지만, 동일한 Map에서 호출하는 keySet 메서드는 같은 Map을 대변하기 때문에 반환한 객체 중 하나를 수정하면 다른 모든 객체가 따라서 바뀐다.
따라서 keySet이 뷰 객체 여러 개를 만들 필요가 없다.

불필요한 객체를 만드는 예시

## 불필요한 객체를 만드는 예 : Auto boxing
기본 타입과 박싱된 기본 타입을 섞어 쓸 때 자동으로 상호 변환해주는 기술로,
기본 타입과 그에 대응하는 박싱된 기본 타입의 구분을 흐려주지만, 완전히 없애주지는 않는다.  

```java
private static long sum() {
    Long sum = 0L;
    for(long i=0; i<=Integer.MAX_VALUE; i++) {
	sum += i;
    }
    return sum;
}
```
위의 방식은 느리다. 와이?

sum변수를 long이 아닌 Long으로 사용해서 불필요한 Long인스턴스가 약 2^31개가 만들어졌다.
(long 타입인 i가 Long 타입인 sum 인스턴스에 더해질 때마다)
Long으로 선언된 변수를 long으로 바꾸면 훨씬 더 빠른 프로그램이 된다.

**박싱된 기본 타입보다는 기본 타입을 사용하고, 의도치 않은 오토박싱이 숨어들지 않도록 주의하자.**

<br>

요즘에는 JVM이 컬렉션 가비지를 통해 작은 객체를 생성하고 회수하는 일이 크게 부담되지는 않는다.

그리고 단순히 객체 생성을 피하기 위해 자신만의 객체 풀(pool)을 만들지 말자..왜 ?
코드를 헷갈리게 만들고 메모리 사용량을 늘리고 성능을 떨어트린다.






DB 커넥션 같은 경우 생성 비용이 워낙 비싸니 재사용 하는 편이 좋지만, 일반적으로 자체 객체 풀은 코드를 헷갈리게 하고, 메모리 사용량을 늘리며 성능을 떨어트린다.

방어적 복사가 필요한 상황에서 객체를 재사용했을 때의 피해가 , 사용하지 않는 객체를 반복적으로 생성했을 때의 피해보다 크다!


가장 최선은 객체를 재사용할지, 방어적 복사를 통해 재사용을 안 할지 상황에 맞춰 잘 판단해야 한다.
