자바 라이브러리에는 close 메서드를 호출해 직접 닫아줘야 하는 자원이 많다.      
예를 들면 InputStream, OutputStream, java.sql.Connection 등등~~

	 
자원 닫기는 클라이언트가 놓치기 쉬워서 예측할 수 없는 성능 문제로 이어지기도 하는데, 일반적으로 try-finally를 사용했다. 
  
<br><br><br><br><br><br>


## try-finally
```java
public static String firstLineOfFile(String path) throw IOException {
    BufferedReader br = new BufferedReader(new FileReader(path));
    try {
        return br.readLine();
    } finally {
        br.close();
    }
}
```

```java
static void copy(String src, String dst) throws IOException {
    InputStream in = new FileInputStream(src);
    try {
        OutputStream out = new FileOutputStream(dst);
        try {
            byte[] buf = new byte[BUFFER_SIZE];
            int n;
            while ((n = in.read(buf)) >= 0)
                out.write(buf, 0, n);
        } finally {
            out.close();
        }
    } finally {
        in.close();
    }
}
```
try-finally 방식은 자원을 명시적으로 직접 닫아줘야 하기 때문에 자원이 많아질수록 코드가 복잡해지고, 자원을 닫는 것을 놓칠 수 있다. 

또한 예외는 try 블록과 finally 블록 둘 다에서 발생할 수 있기 때문에 주의해야 한다.    
    
만약 기기 문제로 물리적인 문제가 생기면 firstLineOfFile 메서드 안에 있는 readLine() 메서드가 예외를 던지고, close() 메서드도 예외가 발생할 것이다.   
이런 경우 두 번째 예외가 첫 번째 예외를 삼켜, 스택 추적 내역에서 첫 번째 예외에 관한 정보는 사라진다. 이로 인해 디버깅이 어려워진다.
   

<br><br><br><br><br><br>


## try-with-resources

try-with-resources를 사용하기 위해서는 해당 자원이 AutoCloseable 인터페이스를 구현해야 한다. 

AutoCloseable는 void 를 반환하는 close 메서드 하나만 정의한 인터페이스이다.

```java
public static String firstLineOfFile(String path) throw IOException {
    try (BufferedReader br = new BufferedReader(new FileReader(path))) {
        return br.readLine();
    }
}
```

```java
static void copy(String src, String dst) throws IOException {
    try (InputStream in = new FileInputStream(src);
        OutputStream out = new FileOutputStream(dst)) {
            byte[] buf = new byte[BUFFER_SIZE];
            int n;
            while ((n = in.read(buf)) >= 0)
                out.write(buf, 0, n);
    }
}
```

readLine과 close 호출 양쪽에서 예외가 발생하면, close에서 발생한 예외는 숨겨지고,readLine에서 발생한 예외만 기록된다.  

close 호출에서 예외가 발생했을 때, close에서 발생한 예외는 숨겨지고 첫 번째 예외가 기록된다.
이렇게 실전에서는 예외 하나만 보존되고 여러 개의 다른 예외가 숨겨질 수 있다.

숨겨진 예외는 suppressed라는 꼬리표(suppressed label)와 함께 스택 트레이스에 나타난다. 즉, 두 번째 예외는 로그에 기록되긴 하지만, 그 예외가 숨겨졌다는 표시를 달고 나타나는데,
getSuppressed() 메서드를 사용하면, 코드에서 이 숨겨진 예외들을 직접 가져올 수 있다.

<details>
	<summary><b>getSuppressed 예제</b></summary>
	
```java
public class ThrowExample {
    public static void main(String[] args) {
        try {
            raiseCustomMultiException();
        } catch (Exception e) {
            e.printStackTrace();
            Throwable[] suppExe = e.getSuppressed(); // 숨겨진 예외를 가져옴

            for (int i = 0; i < suppExe.length; i++) {
                System.out.println("Suppressed Exceptions:");
                System.out.println(suppExe[i]);
            }
        }
    }
    public static void raiseCustomMultiException() throws Exception {

        final IOException ioe = new IOException();

        // 숨겨진 형태로 예외 추가
        ioe.addSuppressed(new NumberFormatException()); 
        ioe.addSuppressed(new NullPointerException());

        throw ioe;
    }
}
```

### 마무리

꼭 회수해야 하는 자원을 다룰 때는 try-finally 말고 try-with-resources를 사용하자.   
코드는 더 짧고 분명해지고, 만들어지는 예외 정보도 훨씬 유용하다.    
try-finally로 작성하면 실용적이지 못할 만큼 코드가 지저분해지는 경우라도, try-with-resources로는 정확하고 쉽게 자원을 회수할 수 있다.
