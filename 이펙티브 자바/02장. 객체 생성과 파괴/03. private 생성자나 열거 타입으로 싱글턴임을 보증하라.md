
# Singleton
인스턴스를 오직 하나만 생성할 수 있는 클래스   
ex) 무상태 객체, 설계상 유일해야 하는 시스템 컴포넌트  



생성자를 private로 만들어 외부에서 new로 호출하지 못하도록 static method로 사용

<br><br>


<br><br>

### 싱글턴을 사용 이유
싱글톤 패턴은 객체를 한 번만 생성하여 재사용이 가능하게 하고, 전역적으로 공유되어 메모리 낭비를 줄이며 다른 객체와 공유가 용이하다.

<br><br><br><br><br><br>


# 싱글턴 생성 방식
### <mark>1. public static 멤버가 final 필드인 방식</mark>
```java
public class Elvis {
    public static final Elvis INSTANCE = new Elvis();
    private Elvis() { ... }

    public void leaveTheBuilding()
}
```
private 생성자는 public static final 필드인 INSTANCE를 초기화할 때 한 번 호출되며, public, protected 생성자가 없기 때문에, Elvis 클래스의 인스턴스를 외부에서 생성할 수 없다.  



#### 장점
해당 클래스가 싱글턴임이 API에 명백히 드러나고, public static 필드가 final이기 때문에 절대로 다른 객체를 참조할 수 없다. 그리고 코드가 간결하다.

<br>
<br>

하지만 리플렉션 API AccessibleObject.setAccessible을 사용해 private 생성자를 호출할 수 있다.  

<br> 

<details>
	<summary><b>리플렉션 API AccessibleObject.setAccessible 예제</b></summary>
	
#### AccessibleObject.setAccessible() 메서드
이 메서드는 클래스의 private 필드, 메서드, 생성자 등에 대한 접근 제어를 우회하도록 한다.

```java
// Elvis 클래스의 생성자 가져오기
Constructor<Elvis> constructor = Elvis.class.getDeclaredConstructor();

// 접근 가능하도록 설정
constructor.setAccessible(true);

// 새로운 인스턴스 생성
Elvis newInstance = constructor.newInstance();
System.out.println("New Elvis instance: " + newInstance);
System.out.println("Original INSTANCE: " + Elvis.INSTANCE);
```

 
</details>



<br>

이 문제를 해결하려면 아래와 같이 두 번째 객체가 생성될 때 예외를 던질 수 있다.
```java
private Elvis() {
  if(INSTANCE != null){
    throw new RuntimeException("생성자를 호출할 수 없습니다.");
  }
}
```

### <mark>2. 정적 팩터리 메서드를 public static 멤버로 제공하는 방식</mark>
```java
public class Elvis {
	private static final Elvis INSTANCE = new Elvis();
	private Elvis() { ... }
	public static Elvis getInstance() { return INSTANCE; }

	public void leaveTheBuilding()
}
```
getInstance()는 항상 같은 객체의 참조를 반환하지만, 이 방법도 리플렉션을 사용해 여러 인스턴스를 만들 수 있다.


<br>
<br>

#### 장점
- **API를 바꾸지 않고도 싱글턴이 아니게 변경할 수 있다.**
```java
class Singleton2 {
    // instance를 ThreadLocal로 변경하여 스레드마다 다른 인스턴스를 제공
    private static ThreadLocal<Singleton2> threadLocalInstance = ThreadLocal.withInitial(Singleton2::new);

    private Singleton2() {}

    // 호출 스레드마다 다른 인스턴스를 반환
    public static Singleton2 getInstance() {
        return threadLocalInstance.get(); // 각 스레드마다 다른 인스턴스를 반환
    }
}

```
<br>

- **싱글턴 패턴을 제네릭을 활용하여 다양한 타입에 대해 유연하게 적용할 수 있다.**
```java
public class Singleton<T> {
    private static Singleton<?> instance;

    private Singleton() {}

    public static <T> Singleton<T> getInstance(Class<T> clazz) {
        return (Singleton<T>) instance;
    }
}
```

<br> 

- **정적 팩터리의 메서드 참조를 Supplier로 사용할 수 있다.**
```java
Supplier<Elvis> elvisSupplier = Elvis::getInstance;
Elvis elvis = elvisSupplier.get();
```

<details>
    <summary><b>Supplier<T></b></summary>
Java 8에서 추가된 함수형 인터페이스로, 값을 공급하는 함수입니다. 이 인터페이스는 인자가 없는 메서드 하나만 정의하고 있으며, 이 메서드는 반환 타입으로 지정된 객체를 반환합니다.
매개변수가 없고 어떤 타입이든지 반환할 수 있습니다.
```java
@FunctionalInterface
    public interface Supplier<T> {
    T get();
}
```
</details>

<br><br>

### 위의 두 방식의 문제?
각 클래스를 직렬화한 후 역직렬화 할 때 새로운 인스턴스가 만들어진다. 
이 문제를 예방하기 위해섯는 readResolve() 메서드를 이용할 수 있다.  

<br><br>



<details> 
    <summary><b>직렬화와 역직렬화</b></summary>
직렬화는 객체를 바이트 스트림으로 변환하는 과정이고, 역직렬화는 직렬화된 바이트 스트림을 다시 객체로 변환하는 과정이다.       
    
#### 왜 역직렬화시 문제가 발생할까?
자바의 역직렬화 메커니즘은 직렬화된 데이터를 사용해 새로 객체를 만들고 그 객체에 저장된 데이터를 채운다.
역직렬화가 이루어질 때, 자바는 클래스 정보를 바탕으로 새로운 인스턴스를 생성합니다. 이 과정에서 원래의 객체가 아니라 새로운 객체가 만들어지게 된다.

이 문제는 모든 인스턴스 필드를 transient로 선언하고 readResolve()메서드를 제공하여 예방할 수 있다.
```java
private Object readResolve() {
    // 진짜 Elvis 반환, 가짜 Elvis는 가비지 컬렉터로
    return INSTANCE;
}
```

### <mark>3. 원소가 하나인 열거 타입을 선언하는 방식</mark>
```java
public enum Elvis {
    INSTANCE; 
	
    public void leaveTheBuilding() { ... }
}
```

```java
public class Main {
  public static void main(String[] args) {
      Singleton instance = Elvis.INSTANCE;

      // 메서드 호출
      instance.doSomething();
  }
}
```
Elvis 타입의 인스턴스는 INSTANCE 하나뿐이다.
이 방식은 복잡한 직렬화 상황이나 리플렉션 공격에도 제 2의 인스턴스가 생성되는 것을 막아준다.
단, 만들려는 싱글턴이 Enum 이외의 다른 상위 클래스를 상속해야 한다면 이 방법은 사용할 수 없다.

## 싱글턴의 한계
1. private 생성자를 갖기 때문에 상속할 수 없다.
2. 테스트가 어렵다
3. 서버환경에서 싱글턴이 하나만 만들어지는 것을 보장할 수 없다.
4. 전역 상태를 만들 수 있기 때문에 바람직하지 않다.
5. 전역 객체로 사용되기 때문에 여러 클래스나 스레드에서 동일한 인스턴스를 공유하게 되어, 여러 객체가 동시 접근할 동기화 문제가 생길 수 있다.
