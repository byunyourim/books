많은 클래스가 하나 이상의 자원에 의존한다.  


SpellChecker는 Dictionary를 사용하고, 의존하는 리소스 또는 의존성이라 한다.

<br><br>

**static 유틸리티를 잘못 사용한 예**
```java
public class SpellChecker {
    // 사전 객체에 강하게 결합
    private static final Lexicon dictionary = ...;

    private SpellChecker() {}

    public static boolean isValid(String word) {return true;}
    public static List<String> suggestions(String typo) {return null;}
} 
```
SpellChecker클래스가 특정 Lexicon객체에 고정되어 있다. 
- 다른 종류의 사전을 사용할 수 없다 -> 유연성 떨어짐
- 내부에서 dictionary 객체를 직접 사용하고 있어 사전 객체를 Mock할 수 없다.
- 따라서, SpellChecker클래스를 독립적인 테스트가 어렵다. 

<br><br>

**싱글턴을 잘못 사용한 예**
```java
public class SpellChecker {
    private final Lexicon dictionary = ...;

    private SpellChecker(...) {
    }

    public static SpellChecker Instance = new SpellChecker(..);

    public static boolean isValid(String word) {return true;}
    public static List<String> suggestions(String typo) {return null;}
}
```

<br>

위의 두 방식 모두 사전을 하나만 사용한다고 가정한다. 


정적 메서드는 **객체의 상태를 저장하거나 자원을 주입받을 수 없기 때문에,** 자원에 따라 동작을 변경하는 것이 불가능하다.
    
싱글턴 인스턴스는 **프로그램 실행 동안 한 번만 생성**되므로, 생성 후에는 자원 변경이 어렵다. 만약 동작에 따라 자원이 변경되어야 한다면, 싱글턴 인스턴스를 새로 생성해야 한다.
   
위의 두 방식 모두 유연하지 않고 테스트가 어렵고, 사용하는 자원에 따라 동작이 달라지는 클래스에는 정적 유틸리티 클래스나 싱글턴 방식이 적합하지 않다.
   
클래스가 여러 자원 인스턴스를 지원해야 하고, 클라이언트가 원하는 자원을 사용해야 할 때 사용하는 패턴이 의존성 주입 패턴이다. 인스턴스를 생성할 때 생성자에게 필요한 자원을 넘겨주는 방식으로, 의존성을 외부로 부터 주입 받는다.

<br><br><br><br><br><br>

## 의존 객체 주입
```java
public class SpellChecker {
    private final Lexicon dictionary;
  
    private SpellChecker(Lexicon dictionary) {
        this.dictionary = Objects.requireNonNull(dictionary);
    }
  
    public boolean isValid(String word) {return true;}
    public List<String> suggestions(String typo) {return null;}
}
```
의존 객체 주입은 유연성과 테스트의 용이성을 높여주며, 불변으로 보장하여 여러 클라이언트가 의존 객체를 안심하고 공유할 수 있다.

<br><br><br>

## 팩터리 메서드 패턴
생성자에 자원 팩터리를 넘겨주는 방식으로
> 팩터리란 호출할 때마다 특정 타입의 인스턴스를 반복해서 만들어 주는 객체를 말한다.
```java
@FunctionalInterface
public interface Supplier<T> {
     /**
     * Gets a result.
     *
     * @return a result
     */
    T get(); // T 타입 객체를 찍어낸다
}
```
Supplier<T>를 입력으로 받는 메서드는 한정적 와일드카드 타입을 사용해 팩터리의 타입 매개변수를 제한해야 한다. 클라이언트는 자신이 명시한 타입의 하위 타입이라면 무엇이든 생성할 수 있는 팩터리를 넘길 수 있다. 

<br>

**클라이언트가 제공한 팩터리가 생성한 타일들로 구성된 모자이크를 만드는 패턴**
```java
Mosaic create(Supplier<? extends Tile> tileFactory) { ... }
```

<br>

```java
import java.util.List;
import java.util.Objects;
import java.util.function.Supplier;

public class SpellChecker {
    private final Supplier<Lexicon> dictionary;

    // Supplier<Lexicon>를 인자로 받는 생성자
    // SUpplie는 인스턴스를 생성할 수 있는 함수형 인터페이스로, get()메서드를 통해 Lexicon 제공
    // Lexicon의 구현체 모른체, 다양한 Lexcion 객체를 생성 시점에 동적으로 주입할 수 있다.
    private SpellChecker(Supplier<Lexicon> dictionary) {
        this.dictionary = Objects.requireNonNull(dictionary);
    }

    public boolean isValid(String word) {
        // dictionary.get()으로 Lexicon 인스턴스를 가져옴
        Lexicon lexicon = dictionary.get();  
        return true;
    }

    public List<String> suggestions(String typo) {
        Lexicon lexicon = dictionary.get();  // dictionary.get()으로 Lexicon 인스턴스를 가져옴
        return null;
    }

    public static void main(String[] args) {
        Lexicon lexicon = new KoreanDictionary();
        SpellChecker spellChecker = new SpellChecker(() -> lexicon);
        spellChecker.isValid("hello");
    }
}

interface Lexicon{}

// Lexicon 인터페이스를 구현한 구체적인 클래스
class KoreanDictionary implements Lexicon {}
class TestDictionary implements Lexicon {}
```

의존성 주입이 유연함과 테스트 용이함을 향상시키지만, 의존성이 많은 큰 프로젝트인 경우에는 코드가 장황해질 수 있다.   

이런 점은 Dagger, Guice, Spring와 같은 프레임워크를 사용해 해결할 수 있다.

## 마무리
클래스가 내부적으로 하나 이상의 자원에 의존하고, 그 자원이 클래스 동작에 영향을 준다면 싱글턴과 정적 유틸리티 클래스는 사용하지 않는 것이 좋다.    

이 자원들을 클래스가 직접 만들게 하는 대신, 생성자에 넘겨주자.
  
의존 객체 주입은 클래스의 유연성, 재사용성, 테스트 용이성을 개선해준다.
